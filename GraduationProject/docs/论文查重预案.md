## 一、先看清风险结构：哪些内容天然不会重复

这是本项目最大的优势——**报告里技术含量最高的部分全是原创工程数据，查重系统无从匹配**。

| 内容类型 | 本项目实例 | 重复风险 | 说明 |
|---|---|---|---|
| **性能优化过程** | 1.6 GB → 333 MB 的完整归因链（NPOT 纹理压缩回退、交叉统计方法、4.5 倍超采样推导） | 🟢 **极低** | 全球独一份的排查过程，通用文献里不可能有 |
| **架构决策与取舍** | 武器/角色解耦三层方案、FSM vs ECS 的具体权衡、事件 struct 零 GC 设计 | 🟢 **极低** | 属于"你的项目怎么做"，不是"通用方法论" |
| **工程数据表** | 169 文件 / 24,479 行 / 10 模块 / 54 clip / 421 帧 / 12 项自检 | 🟢 **极低** | 数字唯一 |
| **工具链细节** | 帽子刚性标尺法、水壶参照法、基线对齐、NPOT 陷阱 | 🟢 **极低** | 具体到工具与参数 |
| **项目专属配置** | 三关主题、8 张知识卡内容、敌人差异化施压节奏 | 🟢 **极低** | 内容原创 |
| **代码** | 全部自研 | 🟢 零 | 代码查重是单独检测项，不是文字查重 |
| **图表** | 架构图、状态机图、管线流程图 | 🟢 零（自绘） | 必须**自己画**，抄图也会被图片查重命中 |

**结论**：本项目的报告**天然低重复**。真正需要警惕的不是技术内容，而是下面这类"通用表述"。

## 二、必须改写的六类高风险表述

这是通用教材/博客里到处都有、查重系统必中的段落类型。**每类给出改写策略**：

### 风险 1：Unity 引擎背景介绍的套话

**典型重复文本**：
> "Unity 是由 Unity Technologies 公司开发的一款跨平台游戏引擎，支持 Windows、macOS、Linux 等多种操作系统。开发者可以通过 C# 脚本编写游戏逻辑……"

**改写策略**：
- 删掉百科式定义，**直接切入你的项目为什么选 Unity 2022.3.62f3c1**
- 用"选型对比"替代"引擎介绍"：从你的实际约束出发（2D 精灵动画 + Animation Event 驱动的命中窗口 + 需要打包 Windows 版 + 项目规模 2.4 万行需要工程化工具）推导选型
- 只保留**与你的决策直接相关**的引擎特性（Animator 状态机、Animation Event、ScriptableObject、asmdef），其余不写

**示例改写**：
> "本项目在引擎选型上需要满足三项约束：其一，动作游戏的命中判定依赖动画帧事件窗口；其二，关卡参数需在编辑器中可视化配置；其三，最终需产出可分发的 Windows 独立版本。Unity 2022.3 LTS 的 Animation Event 机制、ScriptableObject 资产系统与成熟的 Windows 构建管线同时满足这三项约束，故确定以 Unity 为开发引擎。"

### 风险 2：有限状态机的教科书定义

**典型重复文本**：
> "有限状态机是一种数学模型，一个状态机在任一时刻只能处于一个状态……状态之间的转换由事件触发……"

**改写策略**：
- **不讲定义，直接讲你的实现**：`Dictionary<Type, IPlayerState>` 注册、`SwitchState<T>()` 切换、`Enter/Exit/Tick/FixedTick` 生命周期
- 举**你自己的打断优先级**（Die > Hurt > Attack > Dash > Jump > Run/Idle）作为 FSM 的具体体现
- 讲**为什么用 Type 作 key**（避免字符串比较、编译期检查、重构安全）

**示例改写**：
> "项目将玩家行为建模为 11 个独立状态，每个状态实现统一的 IPlayerState 接口，通过 Enter/Exit/Tick/FixedTick 四个生命周期钩子与状态机交互。状态机内部以 System.Type 为键维护状态实例表，SwitchState<T> 完成切换，使状态转移在编译期即可校验，避免了基于字符串标识的重构风险。"

### 风险 3：游戏设计理论的现成论述

**典型重复文本**：
> "游戏设计需要考虑核心玩法循环、关卡节奏、难度曲线等要素……"

**改写策略**：
- 用你的**三关实测数据**代替通用论述：Level01 117 对象 / Level02 199 对象 / Level03 93 对象的构成差异
- 讲你的**差异化施压设计**：近战贴脸 / 远程点射 / 跳跃 / 静态塔四种敌人承担不同节奏
- 难度递进用**具体敌人组合与 Boss 阶段**说明，不用抽象曲线

### 风险 4：环保教育的通用论述

**典型重复文本**：
> "环境保护是当代社会的重要议题……可持续发展是关系到人类未来的战略选择……"

**改写策略**：
- **删掉所有口号式铺陈**，直接从你的 8 张知识卡讲起（塑料瓶 450 年 / 每年 800 万吨塑料入海 / 三角标志 1-7 号树脂）
- 用**具体知识内容**替代抽象倡议：知识卡里的数据本身就是内容，不是论述
- 讲**机制化设计**：怎么把知识做成可收集资产而不是弹窗说教

### 风险 5：性能优化的通用建议清单

**典型重复文本**：
> "为提升游戏性能，可采用对象池、减少 GC 分配、合并 DrawCall、优化贴图压缩格式等措施……"

**改写策略**：
- **不做清单，做案例**。你的对象池、struct 事件、静态数组复用、NPOT 纹理发现——每条都给出"我遇到的具体问题 → 我怎么定位 → 效果如何"
- 数字对比：1.6 GB → 333 MB、GC = 0、12 项自检
- 这部分是你的**高光区**，改写空间大但价值也最高

### 风险 6：结论与展望的套话

**典型重复文本**：
> "本文设计并实现了一个……系统，基本达到了预期目标，但仍存在一些不足，未来将继续完善……"

**改写策略**：
- 不足必须**具体到技术点**（见答辩清单 Q17 的三条真实不足），不要写"功能不够完善""界面还需优化"
- 展望要**对应到已识别的具体技术路线**（骨骼动画 + pose 混合替代逐帧、变形基元库扩展、状态转移覆盖测试 + 性能回归基线做 CI 门禁）

## 三、写作阶段的六条硬规矩

| # | 规矩 | 说明 |
|---|---|---|
| 1 | **每个技术结论后面追问一句"数据从哪来"** | 能指到工程文件/实测数据的段落，天然安全；指不到的段落，多半是套话，删或改 |
| 2 | **通用定义只写一次，且必须"绑到本项目"** | 不要单独开一节讲 Unity 是什么 / FSM 是什么，一律嵌入具体决策叙述 |
| 3 | **图表全部自绘** | 架构图、状态机图、管线图用 draw.io / Visio / PPT 画成矢量图导出，**不截网络图片**（图片查重同样会命中） |
| 4 | **引用要真正引** | 别人的方法论 → 上标引用 + 参考文献；自己的实现 → 明确写"本文设计/本文实现" |
| 5 | **术语优先，句子次之** | 描述实现时多用"状态表 / 事件总线 / 归一化 / 交叉统计 / 超采样"这类**术语化短语**，少用长句铺陈——术语重复率低，且更像工程文档 |
| 6 | **写完立刻自查，不要等交前** | 见下方自查流程 |

## 六、本项目的特殊优势（务必利用）

1. **性能优化章节是天然原创区**：NPOT 纹理压缩回退这个案例，全网公开资料极少，**几乎不可能命中**。这是你报告里最安全也最有技术含量的部分
2. **所有数据可溯源**：169 / 24,479 / 421 / 333MB / GC=0 每个数字都能指到工程文件，**写不出套话**
3. **代码是完整原创**：24,479 行自研代码，且有 2015 行中文注释 + 完整 Git 提交历史支撑"工作量真实"
4. **三份现成材料可直接改写成论文章节**：
   - 《开题报告-要求对照表》→ 选题依据与研究方案章
   - 《答辩问答准备清单》→ 技术实现章的骨架（**每个问答都对应一段可展开的技术论述**）
   - 《性能实测报告》→ 性能优化章

## 七、开题报告当前状态的查重预判

**结论：开题报告（5072 字）重复风险极低。**

理由：
- 四章内容全部**绑定本项目的实测数据与具体技术方案**（架构表、路线表、进度表、成果表）
- 18 条参考文献均为**上标引用**，正文没有大段转述
- 国内外研究现状部分是**综述性引用**（引用他人观点），这部分天然需要引用标注，查重系统会识别为引述
- 摘要与关键词是原创概括

**建议动作**：在提交前用知网自查一次，**记录基线数字**（比如 3.2%）。这个数字既是你后续改写的参照，也是第 ① 条"重复率"核审时老师可能问到的答案 —— **提前知道自己是多少，比被问住强**。
