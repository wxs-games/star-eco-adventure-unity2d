# 性能实测报告

> 测量日期：2026-10-18（初测，Editor）/ 2026-10-19（GC 优化后复测，Build）
> 引擎：Unity 2022.3.62f3c1 | 平台：Windows 11 x64
> 测量工具：ProfilerRecorder 计数器；Build 版为 Development Build + 临时运行时探针
> 测量场景：Title / Level01 / Level02 / Level03

## 一、测量方法

### 1.1 Editor 版（仅用于帧时间与资源统计）

1. 打开目标场景 → 进入 Play 模式 → 等待场景完全初始化（含刷怪、UI、音频）
2. `ProfilerRecorder` 读取 `GC Allocated In Frame` / `GC Allocation In Frame Count` 等计数器

**测量条件说明**：Editor Play 模式下窗口失焦/空闲时采样不刷新，因此采用「场景加载完成后
主动读单帧」的方式取样，反映稳定运行帧而非峰值帧。

### 1.2 Build 版（GC 判定的正式口径）

1. 构建 **Development Build**（Windows x64）
2. 由临时运行时探针（`ProfilerRecorder` 读取 Memory 分类计数器，`RuntimeInitializeOnLoadMethod` 自举）
   在每关场景加载完成后先跳过 2 秒稳定期，再采样 5 秒窗口（约 820 帧）
3. 记录 **均值与峰值**（均值代表稳定态，峰值捕捉加载/异常帧）
4. 探针仅用于测量，测完即从工程删除，不随最终版本发布

### 1.3 为什么 GC 必须以 Build 版判定

2026-10-19 在 Editor 做的对照实验（Level01，同一帧条件）：

| 条件 | GC 分配次数/帧 | GC 字节/帧 |
|---|---|---|
| 全部脚本启用（基线） | 379 | 19,513 B |
| **禁用工程全部 202 个 MonoBehaviour** | 376 | 19,438 B |
| 只启用 UI + Level + Framework | 375 | 19,437 B |
| 只启用 Player + Combat + Eco + EnemyAI + Boss | 374 | 19,397 B |

三者差值仅 3~5 次/帧（75 B），**落在采样噪声 ±5 内**，即 Editor 下的 375 次/帧几乎全部是
编辑器与引擎自身的固定底噪，与游戏代码无关。这解释了 2026-10-18 版报告为何在 Editor 口径下
始终无法把 GC 归零：**该口径本身不可达标**。Unity 官方性能指南同样要求 GC 只应在 Build 版测量。

## 二、实测结果

### 2.1 帧时间（Editor Play 实测，2026-10-18 数据，本次未复测）

| 关卡 | CPU 帧时间 (ms) | CPU 主线程 (ms) | CPU 渲染线程 (ms) | GPU 帧时间 (ms) | 隐含帧率上限 |
|---|---|---|---|---|---|
| Level01 污染星球 | 2.02 | 0.51 | 0.43 | 0.73 | ~495 FPS |
| Level02 生态森林 | 1.93 | 0.53 | 0.41 | 0.15 | ~519 FPS |
| Level03 能源工厂 | 3.42 | 1.01 | 0.61 | 0.94 | ~292 FPS |

**结论**：三关 CPU 帧时间均 < 4 ms，GPU 帧时间均 < 1 ms。
60 FPS 的预算为 16.67 ms，最重的一关（Level03，含 Boss）仅用掉 20.5%，
**「帧率稳定 60」目标达成，余量 4.9 倍**。

### 2.2 GC 分配（Build 版 Development Build，Windows x64）

**优化前**（2026-10-19，仅含 Boss 血条字符串缓存）：

| 场景 | 均值 B/帧 | 峰值 B | 均值 次数/帧 | 峰值 次数 |
|---|---|---|---|---|
| Title | 11 | 8,552 | 0 | 107 |
| **Level01** | **40** | **40** | **1** | **1** |
| Level02 | 0 | 112 | 0 | 2 |
| Level03 | 0 | 0 | 0 | 0 |

**优化后**（消除 Level01 每帧 `FindObjectOfType`）：

| 场景 | 均值 B/帧 | 峰值 B | 均值 次数/帧 | 峰值 次数 |
|---|---|---|---|---|
| Title | **0** | 0 | **0** | 0 |
| Level01 | **0** | 0 | **0** | 0 |
| Level02 | **0** | 112 | **0** | 2 |
| Level03 | **0** | 0 | **0** | 0 |

> 优化前 Level01 的特征是「每帧恰好 1 次分配、恰好 40 字节、均值等于峰值」，
> 属于典型的**单一调用点每帧分配**；Title 的 8,552 B / 107 次是场景加载期的瞬时尖峰，非稳定态。
> 优化后 Level02 仍偶发一次 112 B / 2 次的瞬时分配（非每帧、不累积），保留观察。

### 3.1 每帧分配来源：实测结论（修正 2026-10-18 的推测清单）

2026-10-18 版报告列出的 5 类来源属**未经验证的推测**。本次经「代码审查 + Build 版分组禁用实验」
逐项证伪/修正如下：

| 原推测来源 | 实测结论 | 依据 |
|---|---|---|
| ① LINQ 链式调用 | ❌ **不成立** | 全工程运行时脚本**零 LINQ**（`.Where/.Select` 仅出现在 `Assets/Scripts/Editor/` 一次性工具）；敌人感知早已是 `static readonly Collider2D[8]` + `OverlapCircleNonAlloc` |
| ② 字符串拼接 | ⚠️ **部分成立** | HUD 已在 `f418cc5` 缓存；本轮补修 `BossHealthBar` |
| ③ 闭包/委托 | ❌ **不成立** | 事件订阅全部在 `OnEnable` 一次性完成、传方法组，无每帧 lambda |
| ④ `Camera.main` / `FindObjectOfType` | ❌ **不作为 ④ 描述的现象成立** | `Camera.main` 本身不产生每帧分配，6 处调用 5 处在 `Awake/Start`；真正的元凶是 `FindObjectOfType`（见下） |
| ⑤ 值类型装箱 | ❌ **未发现** | 无 `SendMessage`、无 `object` 参数装箱路径 |

**真正的每帧分配来源（本次定位，共 2 处）：**

1. **`DialogueTrigger.Update` 每帧 `FindObjectOfType<DialoguePanel>()`**（Level01）
   —— 玩家位于对话触发区之内时，该行**每帧**执行；Unity 的 `FindObjectOfType` 内部会分配
   一个匹配对象数组（此处 1 个元素 → 固定约 40 B / 1 次）。Level01 的出生点恰好落在对话触发区内，
   Level02/03 不在，故只有 Level01 中招。
2. **`BossHealthBar.UpdateFill` 每帧 `$"{hp} / {max}"`**（Level03）
   —— 字符串插值每帧产生新字符串并触发 uGUI Text 重建。

**定位方法（可复现）**：Development Build 内按命名空间分组禁用 MonoBehaviour
（`StarEco.UI.` / `StarEco.Eco.` / 其余），命中组即归零，再在组内按单类型二分收敛到具体调用点。
该方法比 Profiler Allocation Callstacks 更快，且不受编辑器噪声干扰。

### 3.2 本轮改动

| 文件 | 改动 |
|---|---|
| `Assets/Scripts/UI/DialogueTrigger.cs` | 新增 `_panel` 字段缓存 `DialoguePanel` 引用，删除 `Update` 内的每帧 `FindObjectOfType` |
| `Assets/Scripts/Boss/BossHealthBar.cs` | 新增 `_lastHp` / `_lastMaxHp`，仅在 HP 数值变化时重生成文本 |

**验证方式**：修改后重新构建 Development Build，四场景复测 → 均值 0 B / 0 次每帧（见 2.2）。

## 四、结论

- **帧率目标保持达成**：三关帧时间均有 4.9 倍以上余量，支撑 60 FPS 稳定运行
- **GC = 0 达成**：Build 版四场景（Title / Level01 / Level02 / Level03）每帧均为 0 B / 0 次；
  优化前 Level01 的 40 B/帧 已定位并消除
- **口径说明**：Editor Play 下约 375 次/帧是编辑器与引擎底噪（已用「禁用全部脚本」对照实验证实），
  **不作为 GC 达标依据**；本报告的 GC 结论一律以 Build 版为准
- **残留观察项**：Level02 偶发一次 112 B / 2 次的瞬时分配（非每帧）；内存占用仍需 Build 版复核
- 论文表述建议：如实呈现「Editor 口径不可达标 → 改用 Build 口径 → 分组禁用定位到 2 处调用点 →
  优化前后量化对比（40 B/帧 → 0）」的完整分析链路
