## 第一组：整体架构（必问）

### Q1. 介绍一下你这个项目的整体架构？

**答题要点**
项目采用**五层分层架构**，共 10 个功能模块、169 个 C# 文件、24,479 行代码：

| 层 | 职责 | 模块 |
|---|---|---|
| **Framework** | 与具体玩法无关的底层设施 | 存档系统、对象池、事件总线、音频管理、运行时自检 |
| **Core** | 全局单例与游戏流程 | 场景流转、游戏状态 |
| **Player** | 玩家角色与状态机 | 移动、动画驱动、工具锚点 |
| **Combat** | 战斗系统 | 攻击状态、命中盒、投射物、伤害计算 |
| **EnemyAI** | 敌人 AI | 状态机基类、感知、三种敌人实现、防御塔 |
| **Eco** | 环保玩法核心 | 净化系统、垃圾堆、破坏物、拾取物、知识卡 |
| **Boss** | Boss 战 | Boss 状态、阶段切换、配置 |
| **Level** | 关卡 | 关卡管理、出生/重生、结算 |
| **UI** | 界面 | HUD、各类面板、图鉴、对话、伤害数字层 |
| **Editor** | 编辑器工具 | 47 个 Editor 脚本（场景自动搭建、批量构建、美术工具） |

**关键设计**：玩法逻辑（Combat / EnemyAI / Eco）**不直接依赖具体实现**，通过事件（`struct` 类型）解耦——例如 `GarbagePurifiedEvent`、`EnemyDamagedEvent`、`LevelPurifiedEvent` 等 10+ 个事件类型，让 UI 层与玩法层互不引用。

**证据**：`Assets/Scripts/` 目录结构；`Assets/Scripts/Framework/FrameworkSelfTest.cs`

**避坑**：不要说"用了 ECS/DOTS"——你没有用，是**传统 Unity 单体游戏架构 + 事件解耦**。诚实说明反而显得可控。

### Q2. 为什么用有限状态机（FSM）而不是直接用 if-else 或 ECS？

**答题要点**
- **FSM 是这个项目的核心组织方式**：玩家 11 个状态（Idle/Run/Air/Land/Hurt/Death/Dodge/Dash/Crouch/WallSlide/Ledge），敌人有独立的状态机基类 `EnemyStateMachine`，Boss 独立一套。
- **不用 ECS 的原因**（这是加分回答，要讲清）：
  1. 项目是**单主角 + 有限数量 AI 单位**的 2D 动作游戏，实体数量在两位数级别，ECS 的数据导向优势发挥不出来
  2. ECS 的实体/组件心智负担对这个体量是**负收益**——本项目更需要的恰恰是"状态转移规则一目了然"
  3. Unity 2022 的 ECS（Entities 包）仍处于相对早期，且 2D 精灵动画（Animator + Animation Event）与 ECS 集成成本高
- **FSM 的具体实现方式**：`PlayerStateMachine` 用 `Dictionary<Type, IPlayerState>` 注册状态，`SwitchState<T>()` 通过类型切换；状态实现 `IPlayerState` 接口，含 `Enter/Exit/Tick/FixedTick` 生命周期。
- **打断优先级**：Die > Hurt > Attack/Interact > Dash > Jump > Run/Idle

**证据**：`Assets/Scripts/Player/PlayerStateMachine.cs`、`Assets/Scripts/Player/PlayerStates.cs`、`Assets/Scripts/EnemyAI/EnemyStateMachine.cs`

**避坑**：不要说"FSM 让代码更好维护"这种空话。要落到**"Attack 状态播到第 5 帧触发投掷、AttackHitbox 在第三段不开窗"**这种具体行为上。

### Q3. 你的代码怎么分层？模块之间怎么通信？

**答题要点**
- 底层（Framework/Core）不引用上层玩法模块，上层通过接口 + 事件反向通知
- **事件全部用 `struct` 传递**，避免每次派发产生 GC 分配——这是 Unity 2D 项目最容易踩的性能坑（`EnemyDamagedEvent`、`DamageInfo`、`BossPhaseChangedEvent` 等都是 struct）
- 静态服务定位：`LevelSaveService` / `CodexService` 这类无状态管理器用 static 类，避免层层注入的样板代码
- 配置用 **ScriptableObject**：`PlayerConfig` / `CombatConfig` / `EnemyConfig` / `EcoConfig` / `BossConfig` / `LevelConfig`，数值调整不碰代码

**证据**：`Assets/Scripts/*/Events/*.cs`（全部 `public struct`）、6 个 Config 类

## 第二组：核心技术难点（高分题）

### Q4. 你项目里技术含量最高的一块是什么？

**答题要点（这是全场最重要的题，务必讲透）**

**构建体积优化：1.6 GB → 333 MB（-79%）**

完整逻辑链（能讲完这条链就是满分）：

1. **现象**：第一次 Windows Release 构建产物体积 1.6 GB，对一个 2D 动作游戏明显不合理
2. **第一步排除**：查 `Assets/` 源文件总量只有 **693 MB**，而进包纹理实测 **240 MB** —— 说明膨胀发生在 Unity 的**导入/打包环节**，不是资源本身太大
3. **第二步定位**：写脚本统计**进包纹理的尺寸对齐性与实际格式**的交叉分布，发现一个 100% 吻合的规律：

   | 尺寸对齐 | 实际格式 | 数量 | 占用 |
   |---|---|---|---|
   | 宽高**都是** 4 的倍数 | DXT1 / DXT5 压缩 | 41 | 30 MB |
   | 任一维度**非** 4 的倍数 | **RGBA32 未压缩（4 字节/像素）** | 395 | **2655 MB** |

4. **根因**：美术管线 `process_sheets.py` 按"内容自适应"生成画格，尺寸是 1200×833、993×1124、1397×1247 这类**非 4 倍数**。而 Unity 的 Automatic 格式选择器对 NPOT（non-power-of-two）纹理会**放弃 BC/DXT 压缩、退回未压缩 RGBA32** —— 整整 4 倍膨胀。
   - **验证**：尝试显式指定 BC7 格式 → **无效**，Unity 不允许 NPOT 纹理用 BC 格式，回退照旧
5. **另一个关键判断**：查了相机 ortho=6.5、1080p 下 1 世界单位=83px、帧 PPU=378，推出**纹理尺寸恒为实际显示尺寸的 4.5 倍**（Player 纹理 1200×833 → 屏幕显示仅 264×183 px）—— 也就是说纹理分辨率**严重过剩**
6. **解法**：批量把纹理导入器的 `maxTextureSize` 设为 **512**（仍 > 实际显示尺寸，属于**超采样，画质零损失**）。纹理存储 **3030 MB → 231 MB**，整包 **1.6 GB → 333 MB**
7. **改完必须验证**：依赖图从 637 → 637 完全一致，1555 个 sprite 资产全部正常加载，55 个 AnimationClip / 46 个 Prefab / 14 个 SpriteRenderer 零 null 引用；实机运行 + 编辑器 Play 模式截图确认角色、敌人、背景、HUD 全部锐利无破图

**这套思路的通用价值**（可以升华）：它不是"改了个参数"，而是**先用交叉统计把异常现象归因到一个可验证的规则，再验证规则的可干预性，最后证明干预无副作用**——这是可复用的排查方法论。

**证据**：`Tools/art-pipeline/process_sheets.py`；纹理导入器批量设置；`Builds/2026-10-29/` 构建产物

**避坑**：一定要讲"为什么 512 是安全的"（因为 4.5 倍超采样），否则老师会问"降分辨率会不会糊"。

### Q5. 你的美术帧是怎么生成的？一条完整管线讲一下。

**答题要点**
自建了一套**逐帧生成 + 程序化处理**的美术管线（`Tools/art-pipeline/`，含 6 个脚本）：

1. **统一背景归一化**：入口把透明底 / 白底 / 黑底素材统一转成 RGBA master（因为后续抠像算法依赖已知背景）
2. **连通域清理**：去掉碎影噪点，但保留白色 T 恤、眼白等真实白色区域
3. **缩放归一化**：以典型身高中位数统一缩放，**脚底基线对齐**（否则帧间会跳动）
4. **画格尺寸策略**：**最高帧定缩放、最宽帧定画格宽** —— 防止横向动作（挥臂、冲刺）被裁切
5. **坏帧处理**：用相邻帧替换

**踩过的坑（很能体现工程能力）**：
- **整网格文生图无法控制每帧姿态**（实测两次都产出 7/8 帧同姿势）→ 改为**统一角色描述串 + 逐帧精确姿态描述逐张生成**，再拼网格过管线
- **逐帧生成的人物占比不一致**（实测比 Idle 大 1.2 倍），且**蹲伏帧常画得比站姿帧更满** → 用「**橙色罗纹帽当刚性标尺**」归一：帽子是纯色刚性部件、不随姿态形变，用它的像素高做标尺缩放到统一值
- **链式参考会"粘住姿势"**（拿蹲姿当参考生成，出来的还是蹲着）→ 要大幅改变身体高度时必须换参考图

**证据**：`Tools/art-pipeline/`（含《美术资源生成流程.md》文档 + 6 脚本）、`Assets/Art/Art/*/Frames/`

### Q6. 你的角色动画是怎么和武器解耦的？

**答题要点**
**问题**：角色帧只画空手（因为要支持两把不同钳子），武器必须外挂，怎么让武器"跟手"？

**解法**（三层配合）：
1. **结构**：钳子是玩家下的 `ToolAnchor` 子物体，pivot 设在**握持点**
2. **位置**：`ToolAnchor` 的 `m_LocalPosition.x/y` 在**同一个 .anim 动画片段内用曲线逐帧驱动**，跟随手部轨迹
3. **显隐**：`m_IsActive` 曲线控制 —— 解耦动作时显示、动作里烘焙了工具时隐藏（保证只有一把钳子）

**效果**：一套角色动画支持两把钳子，不重画美术帧。

**踩过的两个坑（一定要讲）**：
- **排序问题**：角色 `SpriteRenderer.sortingOrder` **进场景后是 15，而预制体里是 0**（因为场景构建脚本 `FixAllLevelSpriteSorting.GuessOrder()` 兜底返回 15）。武器若按"父级 order+1"固化成 1，**会被角色整个盖住，看起来像"钳子消失"**。解法：三处一起处理 —— 预制体构建时 role 直接设 15、排序脚本加 `toolanchor=16`、运行时 LateUpdate 兜底跟随 `_body.sortingOrder + 1`
- **`PlayerToolAnchor` 必须加 `[ExecuteAlways]`**，否则编辑模式下看不到工具，无法调试

**证据**：`Assets/Scripts/Player/PlayerToolAnchor.cs`、`Assets/Scripts/Combat/`

**避坑**：`[ExecuteAlways]` 的 LateUpdate 纠正在编辑器不重绘时**不跑**，不能依赖它兜底——这个细节能显示你真的调试过。

### Q7. 第三段攻击是投掷武器，怎么实现的？高速物体怎么保证不穿透？

**答题要点**
1. **第三段改为投掷**：攻击状态播到第 5 帧（`ThrowReleaseTime`，24fps）时调 `ToolThrow.TryThrow()` 把钳子甩出去
2. **命中判定全部交给投射物**：`AttackHitbox` 在 `CurrentSegment == 3` 时**整段不开窗**，伤害不由角色本体结算
3. **投射物不用物理碰撞**（避免高速穿透），改为**逐帧 `CircleCastNonAlloc` 沿路径扫掠**（静态数组复用，零 GC）
4. **回旋设计**：出程飞满射程 / 撞墙 / 超时折返，回程朝 `ToolAnchor` 归位
5. **投掷期间隐藏工具**：只能改 `SpriteRenderer.enabled`，**不能用 `SetActive`** —— 因为动画曲线每帧会写 `m_IsActive`，会覆盖回来

**工程量体现**：第三段还实现了**边跑边打**——攻击时不再完全锁死水平移动，地面全速、空中按 `AirControlRatio` 衰减；同时删掉了"新按方向就取消攻击"的粗暴逻辑。

**证据**：`Assets/Scripts/Combat/PlayerAttackState.cs`、`Assets/Scripts/Combat/ToolProjectile.cs`

## 第三组：性能与质量（评阅老师会追问）

### Q9. 你的运行时 GC 表现如何？为什么能做到零分配？

**答题要点**
- Build 版本运行时 **GC alloc = 0**
- 关键手段：
  1. **事件全部用 `struct`**（`EnemyDamagedEvent`、`DamageInfo` 等 10+ 个），派发不装箱
  2. **对象池**（`ObjectPool<T>` + `PoolManager`），带**重复归还防御**（同一对象归还两次会被检测并忽略）
  3. 投射物命中检测用 `static readonly RaycastHit2D[16]` 静态数组复用
- **有运行时自检**：`FrameworkSelfTest` 12 项检查在开发期自动跑，包括对象池预热/取出/归还/重复归还防御

**证据**：`Assets/Scripts/Framework/ObjectPool.cs`、`Assets/Scripts/Framework/PoolManager.cs`、`FrameworkSelfTest.cs`

### Q14. 关卡里玩家具体要做什么？（玩法循环）

**答题要点**
核心循环：**移动探索 → 发现污染源（垃圾堆 / 污染区 / 破坏物）→ 用净化喷壶清除 → 拾取掉落物与知识卡 → 提升净化度 → 清理污染源解锁下一关 → 结算**。

### Q16. 遇到解决不了的技术问题你怎么处理的？

**答题要点（这题老师很爱问，考的是工程素养）**
举 **两个真实案例**，讲清"如何定位"而不是"如何解决"：

**案例一：工具链定位（锚点求解）**
- 问题：角色帧需要确定"拳头"位置来挂武器，原始规则是"取面积最小的皮肤块"，但**举拳过顶时命中的是耳朵**（脸被手臂切碎，最小块变成耳）
- 解法演进：规则 A（面积最小块）→ 失败 → 规则 B（排除头部框后取最远点）→ **引入"蓝色水壶参照法"**：排除头部框（帽子 bbox 上扩 10% / 下扩 60% / 左右 15%）内的皮肤碎片，剩余皮肤像素中取**离水壶质心最远**的点为拳尖，沿指向水壶方向退 18px 得掌心 → 垂手/举拳/前伸三种姿态统一成立

**案例二：Unity 场景排序（钳子"消失"）**
- 现象：武器明明挂上了，运行时却看不见
- 定位：对比预制体与场景中同一对象的 `sortingOrder` → 预制体 0、场景 15（`GuessOrder()` 兜底返回 15）
- 修复：三处同时改（预制体 role 设 15 / 排序脚本 toolanchor=16 / 运行时 LateUpdate 跟随）
- **额外收获**：发现 `[ExecuteAlways]` 的 LateUpdate 在编辑器不重绘时不跑，不能依赖它兜底

**答题要点**：强调方法是"**先缩小问题域 → 构造可验证的假设 → 最小实验对照 → 推广验证**"。
