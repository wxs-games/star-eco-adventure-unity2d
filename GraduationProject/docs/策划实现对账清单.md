## 〇、这份清单解决什么问题

毕业设计的文档越写越多、代码越改越快，**「文档说的」和「代码做的」必然漂移**。本文把漂移点集中登记一次，让每一条都落到明确的归属人。

**判定纪律（项目铁律，务必遵守）**：

判断「有」和「无」都要查**三件**——①脚本/文件存在 ②场景或资产按 GUID 有引用 ③代码有调用点。
只看文件存在就当有（= 误判已修），或只看文档记载就当没有（= 误判未做），都会错。
本文所有条目均已按三件核对；标「运行时才能判定」的除外。

**严重度分级**：

| 级别 | 含义 | 处理时限 |
|---|---|---|
| 🔴 **阻断** | 玩家能遇到、且结果与策划意图相反（如跳过核心玩法） | 必修 |
| 🟡 **重要** | 文档与实现不符，可能在答辩中被问倒，或误导后续开发 | 应修 |
| ⚪ **轻微** | 行号、计数、措辞一类漂移，不影响理解 | 择机 |

## 七、方法论沉淀：同一 prefab 的多个实例，**不能靠名字认**

> **这条是本次对账过程中真实踩到的坑**，比任何一条具体偏差都值钱。

### 事件经过

`Puzzle_Pickup`（L3 高台上的净化剂补给瓶）原挂 `y = 3.25`，用户反馈「位置在地板下、捡不到」。
用户代理给的根因分析是：「`SecondFloor` 平台顶面 = 3.65，瓶子在 3.25，低 0.4u 埋在地板里」→ 建议上调到 3.75~3.85。
集成装配发布照此把 y 改成 **3.8**。

**但这个根因分析用错了对象**——主程序 Play 实测时发现：

| 实例 | 位置 | 真实顶面 | 说明 |
|---|---|---|---|
| `SecondFloor` | x = **−2.87** | 3.650 | 段 1，**与拾取物（x=44）根本不在同一段** |
| `Puzzle_Floor` | x = **44.85** | **2.800** | 同一 prefab 的另一个实例，**这才是拾取物脚下的支撑面** |

两者是**同一个 prefab 的两个实例**，改名前缀是 `SecondFloor` / `Puzzle_Floor`，而名字里的 `SecondFloor` 极具误导性——它让人以为「SecondFloor 就是那块地板」，但实际上**那一段的地板叫 `Puzzle_Floor`**。

**结果**：
- 原值 3.25 的真实问题不是「埋在 3.65 的地面下」，而是「圆底 2.55 嵌进 2.80 的地面 0.25u」——**结论一样，原因不同**
- 改成 3.8 后：圆底 3.10，**悬空 0.297u** → 从「埋地下」变成「浮在半空」，**改过头了**

### 教训（写进核对流程）

1. **「某物的支撑面」必须按 x 坐标就近匹配，不能按 prefab 名匹配。** 场景里同名 prefab 的多个实例，名字里的地名/功能名经常是历史遗留。
2. **算地面高度时必须把 `m_Offset` 算进去**：`顶面 = pos.y + m_Offset.y + m_Size.y/2`（还要乘 `m_LocalScale.y`）。本项目 L1/L3 的平台 `m_Offset.y ≈ −0.247`，不算它会系统性高 0.16u（🟡-5 就是这么来的）。
3. **「某对象挂在哪」与「哪个对象是它的地面」是两个独立问题**，必须分别用 x 坐标验证，不能从名字推。
4. **文档里的坐标值本身可能是对的**——`LevelDesign.md` 记的 3.25 与场景一致，是**「3.25 这个值对不对」这个问题本身需要重新推导**，而不是「文档和场景不一致」。这次如果先入为主地认为「文档与场景一致 = 文档对」，就会像用户代理那样把正确的 3.25 当成错的。

### 沉淀成流程

> **核对「物件挂点」类问题时，固定四步**：
> ① 找到该物件所在 x 坐标 → ② 在**同一 x 附近**找支撑面实例（按坐标匹配，不按名字）→ ③ 算 `pos.y + offset.y + size.y/2` 得真实顶面 → ④ 再算物件中心与顶面的关系（贴地 / 嵌入 / 悬空）。
> **任何一步不确定，就标注「待实测」而不是填一个推算值。**
