# 本地化规范 · Localization

> 版本：v1.0 | 2026-10-30 | 维护：策划（文案）+ 程序（取字实现）
> 定位：**中文文案的书写规范 + 文本承载点清单 + 将来做多语言时的迁移路径**。
> 现状一句话：**只有简体中文，没有 i18n 框架，文案分散在 8 类载体里（其中 6 类是硬编码）。** 本文不假装已经支持多语言，它做两件事：把中文写到不出错，把迁移成本算清楚。

---

## 1. 现状：文本承载点清点（实测）

| # | 载体 | 位置 | 条目量 | 可迁移性 |
|---|---|---|---|---|
| 1 | **对白** | `Assets/Resources/Data/dialogues.json` | 14 段 / 36 条 | ✅ 已是 JSON，天然可迁移（加 `Lang` 字段或分文件） |
| 2 | **知识卡** | `Assets/Resources/Data/knowledge_cards.json` | 8 张（标题 + 正文） | ✅ 同上 |
| 3 | **关卡目标文案** | `Assets/Settings/Levels/Level0X.asset` 的 `Label` | 8 条（L1 2 / L2 4 / L3 2） | ⚠️ 在 SO 资产里，需导出成表 |
| 4 | **关卡名/简介** | `UI/LevelSelectPanel.cs`（`LevelCardInfo` 静态数组） | 3 组（名 + 一句话简介） | ❌ 硬编码 |
| 5 | **按钮与面板标题** | 各面板 `UIUtility.CreateButton/CreateText` 调用处 | 约 20 条 | ❌ 硬编码（分散在 7 个文件） |
| 6 | **互动气泡** | `DialogueTrigger` / `SignboardTrigger` / `RescueTarget` / `LeverSwitch` | 4 条（「按 E 交谈」「按 E 阅读」「按 E 解救」「按 E 扳动」） | ❌ 硬编码 |
| 7 | **对话提示** | `DialoguePanel` | 3 条（「按 E 继续」「按 E 结束」「按 E 快进」） | ❌ 硬编码 |
| 8 | **Boss 落幕字幕** | `BossController._epilogueText`（序列化字段） | 1 段 2 行 | ⚠️ 字段可改，但字面量写在代码里 |

> **不在本地化范围**：`Debug.Log` 日志（开发用）、代码注释、异常信息。

**结论**：真正需要迁移的是 1、2、3、4、5、6、7、8 八类；其中 **1、2 已经数据化（占文案总量的 ~80%：36 条对白 + 8 张卡正文），4~8 是硬编码（数量多但每条很短）**。所以"做英文"不是重写游戏，而是**抽 5 个文件的字符串 + 换字体**——半天到一天的工作量。

## 2. 字体与字符集

| 项 | 现状 | 说明 |
|---|---|---|
| 中文字体 | `Resources/Fonts/NotoSansSC-Regular`（SIL OFL 1.1，可随毕设分发） | 走 `UIUtility.BuiltinFont` 统一取 |
| 为什么不用内置字体 | Unity 内置 `LegacyRuntime.ttf`（旧名 `Arial.ttf`）**不含 CJK 字形**，中文会全部渲染成方块 | 踩过，见 `CodeStandard.md` 已踩坑清单 |
| 拉丁/数字 | NotoSansSC 自带完整拉丁与阿拉伯数字，无需 fallback | 所以做英文时字体可以复用 |
| 若将来做日文/韩文 | 需换 `NotoSansJP` / `NotoSansKR`，或改用 TMP + 字体图集 | 当前 UI 是 uGUI `Text`，不支持动态 fallback 链，换语言要换字体资产 |

## 3. 简体中文书写规范

### 3.1 标点与数字

| 规则 | 正例 | 反例 |
|---|---|---|
| 中文句子用**全角**标点 | 「污染核心停转了——工厂的烟囱，第一次透出天光。」 | 用半角 `,` `.` `?` |
| 数字、百分比、单位用**半角** | 「净化剂 12/100」「净化值 60%」 | 「净化值 ６０％」 |
| 省略号用 `……`（六点），不写 `...` | 「这颗星球，重新开始呼吸了。」 | — |
| 破折号用 `——`（两字宽） | 「污染核心停转了——」 | 用 `-` 或 `--` |
| 中文与英文/数字之间**不加空格** | 「按 E 交谈」中的 E 前后空格**保留**（特例，见下） | — |
| **键位字母两侧加空格** | 「按 E 交谈」「按住 K 净化」 | 「按E交谈」 |

> 键位空格是特例：字母是"外来符号"，两侧留空隙更易读，这是游戏 UI 的通行做法（也是本项目全部气泡的现状，不要"顺手统一"掉）。

### 3.2 长度约束（按实际 UI 尺寸反推）

| 元素 | 上限 | 依据 |
|---|---|---|
| 对话框**一行** | **≤ 40 全角字** | 对话框宽 1680px、字号 28 → 约 42 字/行，留 2 字余量 |
| 对白单条 | ≤ 3 行（≤ 120 字） | 超过就拆成两条 `Entries`，让玩家有呼吸 |
| 互动气泡 | **≤ 8 字** | 气泡 400×120px、字号 34 |
| 按钮文字 | **≤ 6 字** | 按钮宽 420px、字号 28 |
| 面板标题 | ≤ 10 字 | 字号 48 |
| 知识卡标题 | ≤ 14 字 | 列表项宽 900px、字号 32 |
| 关卡名 | ≤ 16 字（现状最长 11：「第三关 · 能源工厂的危机」） | 卡片宽 1160px、字号 32 |
| 关卡简介 | ≤ 30 字（现状最长 24） | 卡片内单行 |
| Boss 落幕字幕 | 每行 ≤ 24 字，共 2 行 | 字幕宽 1680px、字号 42 |

**超限时怎么办**：拆句 > 缩字号（仅限 ≤ 2 号差）> 删字。**禁止**用省略号截断叙事文本。

### 3.3 禁止事项

| # | 禁止 | 原因 |
|---|---|---|
| 1 | 在代码里做字符串拼接组句（`"净化值 " + x + "%"`） | 语序随语言变化，拼接无法本地化。**允许**纯数值模板（`$"净化剂 {cur}/{cap}"`，因为只有数字变化） |
| 2 | 在 JSON 里用 `\n` 手工断行 | 换行应由 UI 的 `Text` 自动折行决定；硬断行在小屏/换语言时错位。**例外**：落幕字幕（`_epilogueText`）用 `\n` 分成 2 行，因为它有明确的两行版式 |
| 3 | 用"他/她"指代 Ava | Ava 是 AI 全息投影，统一用「它」或直接写「艾娃」，不用性别代词（`NarrativeDesign.md` §3） |
| 4 | 用感叹号堆情绪（`!!`、`！！`） | 本作基调克制；Ava 是监测站 AI，不激动 |
| 5 | 写"玩家应该……"这类元叙事 | 玩家不该被文本指导，该被场景引导 |
| 6 | 在叙事文本里下环保结论（"所以我们要保护环境"） | 说教；结论由玩家自己得出（见 `NarrativeDesign.md` §6 风格指南） |

## 4. 术语表（必须统一，中英对照为将来留）

| 中文 | 英文（预留） | 定义 | 禁止写法 |
|---|---|---|---|
| 净化值 | Purification | 关卡进度百分比（0~100%） | 净化度、清洁度、环保值 |
| 净化剂 | Purifier | 喷雾消耗的资源（容量 100） | 净化液、药水、能量、燃料 |
| 污染源 | Pollution Source | 可净化的目标（垃圾堆/堵塞点/塔/封锁墙） | 污染物、垃圾（"垃圾"只指 `GarbagePile` 这一类模型） |
| 喷雾 / 喷洒 | Spray | K 键持续操作 | 喷射、喷水 |
| 蓄力净化波 | Purify Wave | L 键蓄满释放的 AOE | 大招、重击、净化弹 |
| 夹钳 | Pliers | 玩家的武器（三段连击） | 钳子（口语可，正式文本用"夹钳"）、武器 |
| 污染度 | Pollution | `1 − 净化值`，驱动刷怪速率与背景色 | 污染程度、肮脏度 |
| 封锁墙 | Sealed Wall | 挡住 Boss 的那面可净化墙（`BossGateWall`） | 大门、屏障、结界 |
| 知识卡 | Knowledge Card | 图鉴条目（8 张） | 卡片、科普卡、词条 |
| 图鉴 | Codex | 知识卡集合面板 | 百科、手册、图集 |
| 监测站 | Monitoring Station | Ava 的载体（AI 全息投影） | 实验室、基地、空间站 |
| 污染核心 | Pollution Core | Boss01 的本体 | 核心、Boss、魔王、怪物 |

## 5. 多语言迁移路径（若将来要做）

### 5.1 三步

1. **抽取**：把 §1 里标 ❌ 的 5 处硬编码抽到 `Resources/Data/ui_strings.json`（键名规范见 §5.2），代码改成 `UiText.Get("btn.start")`。
2. **扩充数据**：`dialogues.json` / `knowledge_cards.json` / `ui_strings.json` / 关卡 `Label` 四处各加语言维度（推荐**分文件**：`dialogues.zh-Hans.json` / `dialogues.en.json`，比在条目里加字段更省心——`JsonUtility` 对嵌套容器的支持有限）。
3. **字体与版式**：换字体资产（若目标语言非 CJK 可继续用 NotoSansSC 的拉丁部分）；按 §3.2 的长度上限**重新校一遍**（英文通常比中文长 30~60%，按钮和气泡最容易溢出）。

### 5.2 键名规范（如果做抽取，一次做对）

```text
<面板/场景>.<元素>[.<序号>]

btn.start            主菜单「开始新游戏」
btn.continue         主菜单「继续游戏」
title.main           主菜单大标题
hud.tank             净化剂条数值模板（含 {0}/{1} 占位）
bubble.talk          气泡「按 E 交谈」
dialog.hint.next     对话「按 E 继续」
level.01.name        第一关名称
level.01.brief       第一关简介
objective.l1.01      第一关目标①
```

**规则**：全小写 + 点分隔；**键名不含语言**；占位符用 `{0}` `{1}` 不用 `%s`（便于 `string.Format`）。

### 5.3 成本估算（诚实）

| 工作 | 量级 |
|---|---|
| 抽 5 处硬编码 + 加 `UiText` 访问层 | 半天 |
| 36 条对白 + 8 张卡 + 8 条目标 + ~20 条按钮翻英文 | 1 天（人工，且质量取决于译者） |
| 版式复查（8 个面板 × 长度重排） | 半天 |
| 回归（三关全流程 + 所有面板） | 半天 |

**约 2.5 人天**。毕设范围外；但因为有本文，**将来任何人接手都知道从哪下手、要改几个文件**——这是写这份文档的实际价值。

## 6. 落地检查清单（新增文案前过一遍）

- [ ] 术语查过 §4 表，没有同义词混用
- [ ] 长度在 §3.2 上限内（对话框 40 字/行、气泡 8 字、按钮 6 字）
- [ ] 全角标点、半角数字、键位字母两侧有空格
- [ ] 没有字符串拼接组句（数值模板除外）
- [ ] 没有硬编码 `\n`（落幕字幕除外）
- [ ] 没有感叹号堆叠、没有元叙事、没有环保结论式说教
- [ ] 对白是"观察"而不是"指令"（Ava 说话像监测站，不像任务发布者）
- [ ] 如果写在 JSON 里，`Id` 命名与既有条目同构（`ava_xxx` / `robot_xxx` / `signboard_xxx` / `kc_xxx`）

## 7. 缺口登记（诚实）

| # | 缺口 | 影响 | 优先级 |
|---|---|---|---|
| L-01 | 无 i18n 框架，5 类文案硬编码 | 无法切换语言 | P3（毕设只交中文） |
| L-02 | 无文本长度校验工具（靠人工数） | 容易溢出 | P3 |
| L-03 | 关卡 `Label` 在 SO 资产里，不在文案表 | 译者找不到 | P3（迁移时一起抽） |
| L-04 | `BossController._epilogueText` 字面量写在代码里 | 改文案要改代码（虽可序列化覆盖） | P3 |
| L-05 | 无「还原默认 / 清除缓存」等系统文案的集中管理 | 分散 | P3 |

> 这 5 项全部 P3：**只有一个语言时，本地化框架是纯成本**。写这份文档的目的不是"现在就做"，而是"现在就把中文写对，将来做的时候有据可依"。
